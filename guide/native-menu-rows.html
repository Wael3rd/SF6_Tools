Adding rows and texts to the game's native menus

Two very different jobs hide behind "add something to a menu". One is a real clone made by a native plugin. The other is borrowing an element the screen already has. Here is how each works, with the exact calls.

The two cases at a glance

Case A · a new row

Clone a control (native C++ plugin)

You need one more object on screen: a row, a spin, a button. The engine builds a copy of an existing control with duplicate, and you register it as a real part of the menu. Lua cannot do this.

Result: 8 rows where the game had 3.

Case B · a text

Borrow a hidden element (Lua)

You need a text somewhere. Screens ship with elements the game keeps hidden. Make one visible, write your string into it, move it. Nothing is created.

Result: same object count, one more of them visible.

Rule of thumb: need a new element → Case A. Need words on screen → look for a hidden text first (Case B), and only clone one if the screen has none to spare.

Case A · Cloning a menu row from a native plugin

Used for the five Drive colour rows on the Edit Character screen (agent MatchingFighterSetting). The recipe comes from LL's OppAlertNative plugin; the code below is the C++ that runs in SF6_MenuRowsNative.dll.

1. Run inside the game's own UI flow, never from a generic tick

Hook the OnUpdate() of the flow that owns the screen and do the work in the post hook. Called from UpdateBehavior, duplicate returns a half-built native object and the managed VM dies on it.

// which flows tick while the screen is open (measured with a probe)
hook_main("app.UIFlowMatchingSetting.Main");
hook_main("app.UIFlowMatchingFighterSetting.Main");
hook_main("app.UIFlowUI10505.CharaSetting");   // character-select panel

bool hook_main(const char* type_name) {
    auto* type = reapi().tdb()->find_type(type_name);
    auto* m = type ? type->find_method("OnUpdate()") : nullptr;
    return m && m->add_hook(update_pre, update_post, false);
}
void update_post(void**, REFrameworkTypeDefinitionHandle, unsigned long long) {
    if (++g_check % 10) return;     // one check every ten passes is plenty
    ensure_rows();
}

2. Find the agent, its parts manager and the row to copy

Agents live in app.UIAgentManager._Entries; each has a GameObject whose name is the screen. The parts are reached through _PartsManager and, recursively, each part's <ChildManager>k__BackingField. Match the control by its get_Name().

auto* pm     = field(agent, "_PartsManager");
auto* source = find_part(pm, "p_Spin_color", 0);   // the model row (Color)
if (find_part(pm, "p_Spin_drvimpact", 0)) return;  // already created for this agent

3. The five calls that make a real row

The control name carries the part class: p_<Class>_<Name>, so UIPartsManager.Create knows to build a UIPartsSpin for p_Spin_drvimpact. Positions are derived from the last two existing rows.

auto* src      = control(source);                          // via.gui.Control of the model part
auto* parent   = obj(src, "get_Parent()");
auto* manager  = obj(source, "get_Manager()");            // app.UIPartsManager
auto* group    = field(manager, "<OwnerParts>k__BackingField");
auto* children = field(group, "_Children");              // List<app.UIPartsItem>
const int layout = number(source, "get_Layout()");

// 1. clone the control (name = "p_Spin_" + row)
auto* clone = obj(src, "duplicate(System.String)", { create_utf8_string("p_Spin_drvimpact") });
// 2. attach it where the model lives
call(parent, "addChild(via.gui.PlayObject)", { clone });
// 3. turn the control into a part (a spin, deduced from the name)
auto* part = obj(manager, "Create(via.gui.Control,via.gui.Control)", { clone, parent });
call(part, "set_Layout(app.UIPartsItemLayout)", { arg_i32(layout) });
// 4. register it in the navigation list, with its index
const int index = number(children, "get_Count()");
call(children, "Add(app.UIPartsItem)", { part });
call(part, "set_Index(System.Int32)", { arg_i32(index) });
call(part, "set__IsLoop(System.Boolean)", { arg_bool(true) });
// 5. place it one step below the last row and name it
call(clone, "set_Position(via.vec3)", { pos });        // y = y_last + step * (k+1)
write_text_message(child(clone, "e_text_title"), "Drive Impact");

4. What the clone gives you

  • A real managed part: Lua finds it afterwards by name (p_Spin_drvimpact) and drives titles, values, chips, left/right and confirm exactly like the game's own rows.
  • Its whole sub-tree (background, title, value text, arrows, colour chips) came with the copy.
  • A hidden row is possible: create it with set_IsDisable(true) and invisible, show it later (the character-select panel does this for a fifth "Special Attacks" row).
  • Nothing is removed on close: the game tears the screen down itself.

Do not

  • Do not call duplicate from Lua or from UpdateBehavior: the object comes back unfinished and the C# / Lua wrapper's refcount kills the VM (crash at StreetFighter6.exe+6F2571C, seen twice).
  • Do not add an item to _ItemList from Lua without a control behind it: prefabs have a fixed pool of controls, an item without one crashes in UIPartsManager.get_AllParts.

Case B · Borrowing a hidden text from Lua

Used for the "Move" and "Zoom" camera hints of the colour editor. The Edit Character screen contains three camera hint blocks under the agent's main control, c_00, c_01 and c_02. The game only shows c_01 ("Rotation"). The other two are complete blocks, just hidden.

1. Reach the block through the agent's main control

local cm  = agent:call("get_ControlMain")
local blk = find_name(cm, "c_02", 0)          -- walks get_Child / get_Next, matches get_Name
local title = find_name(blk, "e_text_title0", 0)

2. Write the text, only when it changes

set_Message with the same string twice crashes in UIPartsItem.UpdateFocus. Always compare first. Do it on the game thread (a post hook or LateUpdateBehavior), never from re.on_frame.

if tostring(title:call("get_Message")) ~= label then
    title:call("set_Message", label)                -- label = L("hint.zoom"), from the locale files
end
title:call("set_Position", Vector3f.new(158, 96, 0))   -- a via.gui.Text's position is its centre

3. Show the block and re-assert what the game rewrites

The block's icon texts are managed by the game (rewritten whenever the input device changes), so the mod writes them again every tick, keyboard or pad.

local panel = find_name(blk, "p_InputGuide_LT_s_aUIScaleDown", 0)
panel:call("set_Visible", true)
local t = find_name(panel, "e_text_0", 0)
local glyph = pad and "<ICON BtnL2>" or "<ICON MouseWD>"
if tostring(t:call("get_Message")) ~= glyph then t:call("set_Message", glyph) end
t:call("set_FontSize", ref_size)                  -- copied from the Rotation block's icon text
blk:call("set_Position", Vector3f.new(1648, 508, 0))
blk:call("set_Visible", true)

Finding something to borrow

  • Walk the control tree and list elements whose get_Visible() is false or whose get_ActualVisible() is false with visible parents: the latter is a ForceInvisible lock, lifted with set_ForceInvisible(false) (that is how each Options row got a badge, reusing its hidden p_InputGuide_0_dUIOptionExtraButton).
  • Prefer texts of the same prefab and font slot as your target; the game's popups keep a few hidden ones (e_text_round, e_text_ready, e_txt_wait).
  • Markup works in these strings: <color RRGGBB>…</color>, <ICON KeyTab>.

Thread and lifetime rules that cost a crash each

  1. GUI writes only on the game thread: a post hook of the flow, or LateUpdateBehavior. re.on_frame is the render thread: read there, never write.
  2. Never write into a cached object the game may have freed (screen closed, character changed). Re-find it, or check sdk.is_managed_object and skip during pause / HUD transitions.
  3. set_Message with an unchanged string crashes. Compare with get_Message first.
  4. Never rewrite a dialog's big title (e_title, bound to the message system) and never End() the focused dialog: replace the page instead.
  5. Clones: plugin, inside the flow's post hook. Not Lua, not UpdateBehavior.
