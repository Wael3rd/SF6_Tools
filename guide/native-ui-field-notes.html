SF6 Native UI Field Notes

Everything that bit us while injecting real, game-drawn UI into SF6's training pause menu — rows, tabs, spins, dialogs, texts, a bottom bar — from Lua and two small native plugins, without touching prefabs or drawing anything ourselves. Each entry is one measured failure: what we saw, what was actually happening, what we ship now, and what we tried first and threw away.

Written for another modder working on the same surface. Dates are 2026. Addresses and method names are from the current game build and will drift.

Pause-menu rows & tabs

app.training.TrainingManager.AddDynamicMenu(TrainingFuncType.DYNAMIC, TrainingMenuData, Action), TrainingMenuFunc.Function / ViewUpdate / GetOptionText / GetOptionIndex, UIFlowTrainingMenu.Param. The game builds the row; we only feed data and answer its callbacks.

FuncType 345 (DYNAMIC) is shared with the game

Silent bug
Symptom
In Battle Hub training the game's own "End Training Session" row vanished after a script reset, then came back but did nothing.
Cause
The game also uses FuncType 345 for its runtime rows. Our "purge unknown DYNAMIC rows" removed them; a blanket early-return in the Function hook then swallowed their click.
Fix
Discriminate by ownership, not by type: a game row carries a real delegate in its DynamicChildData (an Action field), ours pass nil. No purge, no fixed tab-count threshold. Field found by scanning the type definition for Action/Delegate/Func.
Where
NativePauseMenu.lua, game_owns_dyn() · Sep 12–13

AddDynamicMenu clones your data

Silent bug
Symptom
Rows registered early or during pause: the pause menu opened as an empty panel with the guide bar still drawn; only a game restart repaired it. Address comparisons never matched.
Cause
The game copies the TrainingMenuData into tab.DynamicChildData. Touching _ChildData yourself corrupts the layout.
Fix
Identify rows by the 16-byte _MessageID GUID, never by address. Register once, ≥5 s after entering training, never while paused.

NativePauseMenu.lua · Aug 30–31

A FuncType of your own gets no renderer

Silent bug
Symptom
Tempting idea (it works in another modder's C# branch for the options of a real game spin): give each of our rows a FuncType above TrainingFuncType.MAX (346) so the game's callbacks identify it without sharing 345. On one of our rows: the page came up empty, then showed the neighbouring sub-page under the wrong tab. No crash.
Cause
The flow picks its rendering path on FuncType == DYNAMIC; an unknown type only gets Function(347, …) at the page build and nothing else — no ViewUpdate, no GetOptionText, no row. Put on an option instead, the custom type is never read at all on the DYNAMIC path.
Fix
Dropped after one probe each. Ownership stays the delegate of DynamicData (above). The idea only holds for options of a real game spin, where Function receives the option's type on select.

Texts, GUIDs and managed strings

All our texts are fake GUIDs written into _MessageID fields and resolved by a pre-hook on app.helper.hMsg.GetMessage that returns a managed string we own.

Only strings may enter the GUID table

Crash
Symptom
Opening "Download Loadouts": the ticker starts drawing, then a crash. Ten guard patches over two days changed nothing.
Cause
Rows registered with a function as description (lazy text) stored that function raw. The GetMessage hook handed it to sdk.create_managed_string, which returned nil; nil:add_ref() blew up inside the post-hook and left the menu state corrupted.
Fix
text_only() evaluates any function and coerces to string at registration time; managed_string() returns nil instead of indexing nil. Found by bisecting commit by commit against a known-good build — the guards were all treating symptoms.
Where

Dialogs, windows and spins

Our windows are OptionSettingUnits injected into OptionManager: rows, toggles, sliders and spins generated by the game's own option dialog. Rows are clones of native SettingParams, never fabricated instances (that one was a NullReference on day one).

end_dialog() on SAVE — the collector thread reads −1

Crash
Symptom
Access violation on the collector thread at 0x146f23437 / 0x146f25873, on SAVE only; RESET never crashed.
Cause
Ending the focused dialog and the whole stack in one frame leaves nothing holding focus; being listed in the General list is what roots our unit tree for the native GC, and we removed the root while the tree was still displayed. RESET went through replace + pop (new dialog started before the old one ends).
Fix
Every close path now uses replace + pop; the parent is kept alive 8 ticks by the seamless-open logic. The big title e_title is never written directly — statuses ("SAVE OK!") come from a page rebuild.

D

Threads

RE Engine runs UI, input and rendering on different job threads. Lua is not. Most of our unexplained crashes were a Lua callback on the wrong thread.

Rule zero: GUI writes only from LateUpdateBehavior

Crash
Symptom
"Random" crashes minutes into a session, never with the REFramework menu open.
Cause
Bisected with a soak script, 3 cycles per configuration: Lua hooks on HUD text setters / InputState.Update crashed 3/3 with, 0/3 without. The open REFramework menu masked it because input updates stop while it is shown.
Fix
No GUI writes from re.on_frame, on_script_reset, BeginRendering or any hook that runs on a job thread. Everything goes through re.on_pre_application_entry("LateUpdateBehavior").
Where
Aug 29, house rule 1

on_script_reset runs on the reset thread

Crash
Symptom
A set_Message restoring a text during reset → AV.
Fix
Restore on the first game-thread tick after the module loads.

is_managed_object is not a liveness proof

Crash
Cause
It validates a pointer, not that the chunk was not reallocated to another object during a pause/HUD transition.
Fix
Drop caches entirely on those transitions; re-resolve later instead of writing.

Native plugins must be built with /EHa

Freeze
Symptom

The bottom bar, by data (solved after two failed generations)

Silent bug
Symptom
Generation 1 borrowed texts and wrote them from Lua: six crashes in a day in set_Message on freed texts after reloads and mode changes; texts made with sdk.create_instance die on reset. Generation 2 hooked UIWidget_InputGuide.ApplyData and pushed entries into the widget's _InputGuideList (Add / SetAdditionalMessage / Remove juggling on every focus change). It worked, but it fought the game for a list the game owns.
Cause
The bar has one source of truth: every frame the flow calls TrainingManager.GetGuideData(focused TrainingMenuData, List<InputGuideData>, List<String>) and draws from that list. The two lists are created inside the call — unreadable in a pre-hook, reachable in the post-hook through the reference slot (sdk.to_valuetype(sdk.to_ptr(addr), "via.mat4"):read_qword(0) then to_managed_object).
Fix
Post-hook of GetGuideData: identify the focused row (our GUID, or a provider for game rows), Add our cached InputGuideData objects, done. Five probes fixed the rules: an appended entry is drawn after the game's and laid out by the game (x = previous x + previous width, reflow is automatic); two entries sharing a button are merged (our first clones were invisible for that reason alone); Type = 2 (Digital) + DigitalId shows the device glyph and the button's own label — the MessageId is ignored; Type = 5 (Text) shows AdditionalMessage raw, no glyph; Type = 0 (DigitalConfig) + DigitalConfigId + a message GUID shows the glyph of the device in use and our text (the game's own NewInputItem(Int32, Digital.ConfigId, Guid) overload). ConfigIds: UI_DECIDE 90 (F), UI_CANCEL 91 (Esc), UI_X 92 (R / pad X), UI_Y 93 (T / pad Y), LB/RB 94/95, LT/RT 96/97. Fields of app.InputGuideData: Type +0x10, DigitalConfigId +0x14, DigitalId +0x1C, GuideId +0x24, MessageId (Guid) +0x28, AdditionalMessage +0x38 — all <Name>k__BackingField. The hint is display only: the key press stays yours to detect.

Loader and REFramework

Things about the scripting host itself that cost us a day each.

200 locals per chunk

Gotcha
Symptom
"too many local variables (limit is 200)" on the big modules.
Fix
Wrap blocks in do … end, or hang related state on one table.

The do-block cure has its own disease: forward references

Silent bug
Symptom
"Delete slot name" (R / G / pad X) silently did nothing for days, while "Edit slot name" (T) on the same rows worked.
Cause
Wrapping a module section in do … end to dodge the 200-locals limit makes every local function inside it invisible after the block. set_slot_name lived inside, the key handler outside: the call resolved to a nil global, and the pcall around the handler swallowed "attempt to call a nil value".
Fix
Forward-declare (local set_slot_name before the block, assign inside). After any do-block refactor, script the check: every local function defined inside and called after the block must have a forward declaration — a parser pass does not catch this.

H

Raw memory and native plugins

Lua cannot write native memory; a small C++ plugin does it from a relay file. Every address in that file is a promise about the future.

The Fighter Settings freeze: a render-layer iterator spinning on freed memory

Freeze
Symptom
Game frozen at 100 % of one core, window still responding; REFramework logging "Last chance encountered for hooking" every 11 s. No exception, no dump.
Cause
Live minidump: the render job thread was looping in the engine's via.render.RenderLayer tree iterator (+0x40 parent, +0x48 children, +0x50 count), searching for a ShadowCast node that had been freed and reallocated mid-traversal. Upstream: the relay's raw writes (W <addr> <val>, guarded only by "page is writable") landed on effect objects freed by a preview reload; the effect manager was recycled at the same address, so the block key still matched.
Fix
Every write carries its origin (W addr val orig [obj typeinfo]). The plugin samples each address when the relay loads, and writes only if the dword still equals the origin / the requested value / the sample / a value it wrote before / the same saturation-value colour, and only if the owning object still has the same type-info pointer. Lines without origin are refused. Verified: no freeze, no colour regression, refused-write counter in the log.

The rules that survived

Numbered because they are, in fact, the order we learned them in.

  1. GUI writes only from LateUpdateBehavior. Not from on_frame, not from a reset, not from a render hook, not from an input hook.
  2. A valid pointer is not a live object. On any pause/HUD transition drop every cache and re-resolve later.
  3. Never create a control from Lua. Borrow a hidden one, clone by data, or build it from inside the flow in C++.
  4. Never call the game's UI back from its own update. Set a flag, act two ticks later.
  5. Identity is the GUID, ownership is the delegate. Addresses lie (clones), types lie (345 is shared).
  6. Strings only, one extra ref, fresh GUID per call. Anything else in the text table is a crash with a two-day fuse.
  7. Sixteen entries per spin, thirteen rows per page. Measured on the game's own menus.
  8. Close dialogs by replace + pop. Ending the focused dialog and its stack in one frame de-roots a tree the collector is still reading.
  9. Every raw write carries its origin. Page-writable is not the same as still-yours.
  10. /EHa or nothing. A caught AV that skips destructors is a deadlock, not a recovery.
  11. Feed the game's data, don't draw over it. The bar, the rows, the texts: find the call that builds them and answer it; the moment you write into a widget the game also writes, you are racing it.
  12. Read the stack first. No Lua or plugin frame means it is not your bug; copy the log before the next launch erases it.
